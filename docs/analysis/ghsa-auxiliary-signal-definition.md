## 1. 개요 및 분석 목적

Watchback 데이터 파이프라인에서 **주요 위험 신호(Primary Signal: EPSS 급등, CISA KEV 등재)**가 재검토 발화의 트리거 역할을 한다면, **GHSA 보조 신호(Auxiliary Signal: 심각도, 영향 버전, 패치 정보 변화)**는:
1. 취약점의 **현재 기술적 심각도(Severity Baseline: B축)**를 평가하여 우선순위(P0~P3)를 차등 부여하고,
2. **패치 등장 여부(Actionability Change: C축)**를 파악하여 과거에 'No Fix'로 방치된 취약점이 현재 즉시 조치 가능한지 판단하며,
3. **공격 용이성 문맥(Exploitability Context: Deadly Trio)**을 해석하여 웹 UI에 직관적인 설명 문구를 제공합니다.

본 문서는 1년치 실제 Reviewed GHSA 데이터(10,616건)와 과거 6개월 스냅샷(2,546건)을 비교 분석하여 GHSA 속성의 통계적 유효성을 입증하고 보조 신호를 공식 정의합니다.

## 4. GHSA 보조 신호 정의 및 판정 기준

### 4.1. [B축] 현재 심각도 신호 (Current Severity)

| 구분 | 판정 조건식 | 비즈니스 목적 |
| :--- | :--- | :--- |
| **최상위 심각도 동시 충족** | `severity == 'critical' AND cvss_score >= 9.0` | 파괴력과 위험도가 모두 최상위인 취약점에 최대 우선순위 부여 |
| **고심각도 단일 충족** | `(severity == 'critical' AND cvss_score < 9.0)`<br>OR `(severity != 'critical' AND cvss_score >= 9.0)` | 공식 심각도와 CVSS 점수 간의 불일치 보정 |
| **중상위 심각도 충족** | `severity != 'critical' AND 8.0 <= cvss_score < 9.0` | High 등급 및 8점대 고위험군 기본 가중 부여 |

---

### 4.2. [C축] 조치 가능성 변화 신호 (Actionability Change)

| 구분 | 판정 조건식 | 선정 사유 템플릿 문구 |
| :--- | :--- | :--- |
| **공식 패치 신규 출시** | `prev.first_patched_version IS NULL`<br>AND `curr.first_patched_version IS NOT NULL` | `"과거에는 패치가 없었으나 공식 패치 버전({patched_version})이 출시되었습니다."` |
| **패치 버전 상향·변경** | `prev.first_patched_version != curr.first_patched_version` | `"패치 버전이 {prev_version}에서 {curr_version}(으)로 상향/변경되었습니다."` |

---

### 4.3. 공격 용이성 문맥 신호 (Exploitability Context — Deadly Trio)

CVSS Vector 문자열 파싱을 통해 웹 UI에 직관적 해설 코멘트를 생성합니다.

* **네트워크 원격 공격 (`AV:N`)**: 로컬/인접망 접근 없이 인터넷을 통해 원격 공격 가능
* **무인증 공격 (`PR:N`)**: 시스템 권한이나 계정 로그인 없이 공격 가능
* **사용자 개입 불필요 (`UI:N`)**: 피싱 클릭 등 사용자의 상호작용 없이 자동 공격 가능
* ➔ *표출 예시*: `"네트워크 원격 공격 가능, 별도 인증 불필요, 사용자 상호작용 불필요"`

## 6. [완료 기준 3] 데이터 갱신 시점 차이(Time Lag) 및 신호별 해석 한계

### 6.1. 갱신 시점 차이 (Data Latency & Time Lag)
1. **일일 배치(EPSS) vs 비정기 이벤트(GHSA)**:
   * **EPSS**: FIRST.org에서 매일 00:00 UTC 기준으로 전 세계 CVE를 일괄 재산정하는 **24시간 일일 배치 주기**입니다.
   * **GHSA**: GitHub 보안 분석가의 인간 검토 및 패치 배포 시점에 비정기적으로 갱신되는 **이벤트 기반 주기**입니다.
   * *영향*: 패치 출시 또는 심각도 수정 이벤트 발생 후 EPSS 모델에 반영되기까지 **최대 24~48시간의 시차**가 존재합니다.
2. **CVE 발급 지연에 따른 신호 공백 (Backfill Latency)**:
   * 전수 조사 결과, 취약점 공개 후 공식 CVE 번호가 확정되어 매핑되기까지 **평균 1개월 ~ 6개월의 지연**이 발생합니다 (과거 스냅샷 No-CVE 341건 중 56건(16.4%)이 6개월 후 CVE 부여 확인).
   * 이 기간(No-CVE 상태, 약 15.7%) 동안은 EPSS/KEV 점수가 산출되지 않으므로, **GHSA 심각도와 패치 정보만으로 위험을 방어해야 하는 한계**가 있습니다.

---

### 6.2. 신호별 해석 한계

1. **패치 변경(C축)의 해석 한계 (Actionability $\ne$ Risk)**:
   * 패치 신규 출시나 버전 상향은 공격 위험도 자체의 상승을 의미하지 않으며, **'개발자가 이제 조치할 수 있게 됨'을 나타내는 조치 가능성(Actionability) 신호**입니다.
   * 따라서 C축 단독으로는 위험을 과대평가하지 않으며, 반드시 A축(위험 변화) 또는 B축(심각도)과 결합하여 평가합니다.
2. **심각도(B축) 상향의 유효성**:
   * 취약점 공개 이후 새로운 공격 벡터가 발견되어 `ghsa_severity`가 상향(예: `medium` ➔ `critical`)된 경우에만 의미 있는 보조 신호로 인정합니다. 정적인 상태 유지는 점수 가중치로만 활용합니다.
3. **Withdrawn(철회) Advisory 처리**:
   * 오탐(False Positive)으로 판명되어 철회된 취약점(`withdrawn == true`)은 점수 계산 없이 즉시 제외(Gate Filter)해야 노이즈를 방지할 수 있습니다.
