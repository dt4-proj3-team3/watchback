# Watchback 제품 백로그

| 항목 | 내용 |
| --- | --- |
| 제품 요구사항 | [Watchback PRD](prd.md) |
| 스프린트 실행 계획 | [Watchback SP1 Backlog](sp1-backlog.md) |

## 1. 목적

이 문서는 프로젝트 기간에 고려하는 Watchback의 Epic과 사용자 스토리·기술 Task를 우선순위별로 관리한다. 현재 스프린트의 설계·구현·검증 작업은 Sprint Backlog에서 관리하고, API와 데이터 구조는 구현 과정에서 생성하는 계약과 코드가 원본이 된다.

## 2. 우선순위

| 우선순위 | 의미 |
| --- | --- |
| P0 | 핵심 사용자 흐름을 완성하기 위해 반드시 구현 |
| P1 | P0 완성 후 프로젝트 기간에 구현할 확장 범위 |
| P2 | 프로젝트 기간에 여력이 있을 때 검토할 후보. 구현 대상으로 확정되면 수용 기준을 구체화 |

장기적인 Future Scope는 이 문서에서 관리하지 않는다.

## 3. 사용자와 Core User Flow

| 사용자 | 역할 |
| --- | --- |
| 검토자 | 위험 변화와 저장소 맥락을 확인하고 재검토 및 조치 필요성을 판단한다. |
| 조치자 | 요청받은 패키지 업데이트를 수행하고 PR·CI·해결 상태를 확인한다. |

조직에 따라 같은 사람이 검토자와 조치자를 모두 맡을 수 있다. 위험 수용 권한은 별도 사용자 유형을 만들지 않고 조직 정책에 따라 검토자에게 부여한다.

```text
이번에 다시 볼 Alert 확인
→ 선정된 이유와 변화 확인
→ 검토 결과 기록
→ 패키지 단위 조치 후보 확인
→ 업데이트 및 해결 여부 확인
```

## 4. Epic 1 — 위험 변화 재검토

누적된 Alert 중 다시 볼 항목을 선별하고, 변화 근거를 확인해 검토 결과를 남긴다.

### US-01. 재검토 대상 확인

**우선순위: P0**

> 검토자로서, 누적된 Alert 중 유의미한 재검토 대상만 확인하고 싶다. 그래야 전체 Alert를 반복해서 확인하지 않고 제한된 시간을 중요한 항목에 집중할 수 있다.

수용 기준:

- 다시 볼 Alert 목록과 후보 수를 확인할 수 있다.
- 전체 관찰 Alert 대비 후보가 얼마나 줄었는지 확인할 수 있다.
- 각 후보의 저장소, 패키지, 취약점 식별자와 대표 재검토 사유를 목록에서 확인할 수 있다.
- 중요도와 변화 유형을 기준으로 목록을 좁힐 수 있다.
- 후보가 없는 경우 현재 다시 볼 항목이 없음을 확인할 수 있다.

### US-02. 변화 근거 확인

**우선순위: P0**

> 검토자로서, Alert가 왜 지금 다시 선정됐는지 알고 싶다. 그래야 현재 조치가 필요한지 판단할 수 있다.

수용 기준:

- 이전에 관찰된 상태와 현재 상태를 비교할 수 있다.
- EPSS 변화, KEV 등재, 패치 등장 등 선정에 사용된 변화를 시간순으로 확인할 수 있다.
- 저장소 중요도와 패치 가능 여부가 우선순위에 어떻게 반영됐는지 확인할 수 있다.
- 데이터 출처와 기준 시점을 확인할 수 있다.
- 시스템이 실제 악용 여부를 확정하지 않는다는 점이 명확히 표시된다.

### US-03. 검토 활동 기록 및 조치 연결

**우선순위: P0**

> 검토자로서, Alert를 검토하며 수행한 활동과 필요한 조치 업무를 연결하고 싶다. 그래야 이전 작업을 확인하면서 실제 패치 업무는 기존 협업 도구에서 이어갈 수 있다.

수용 기준:

- 검토자가 수행한 활동의 유형과 필요한 메모를 남길 수 있다.
- 외부 티켓 또는 PR 링크를 활동과 연결할 수 있다.
- 작업자와 작업 시각을 확인할 수 있다.
- 이전에 기록된 활동을 시간순으로 확인할 수 있다.
- 외부 티켓의 작업 설명과 진행 이력을 Watchback에 중복해서 관리하지 않는다.

### US-04. 시스템성 변동 요약

**우선순위: P0**

> 검토자로서, 여러 취약점이 같은 시점에 함께 움직인 경우 개별 Alert 대신 요약해서 보고 싶다. 그래야 모델·피드 변화로 알림이 폭증하지 않는다.

수용 기준:

- 시스템성 변동으로 분류된 후보 수와 발생 시점을 확인할 수 있다.
- 시스템성 변동 후보는 기본적으로 개별 재검토 목록을 늘리지 않는다.
- 해당 변동과 연결된 고객 Alert 범위를 확인할 수 있다.
- KEV 등 별도의 중요한 변화가 확인된 항목은 개별 재검토 후보로 구분된다.
- 시스템성 변동으로 판단한 근거를 확인할 수 있다.

## 5. Epic 2 — 조직 단위 조치

재검토 결과를 기간·패키지 단위로 묶고 실제 업데이트와 해결 확인까지 연결한다.

### US-05. 기간별 조직 위험 변화 요약

**우선순위: P1**

> 검토자로서, 일정 기간 발생한 재검토 후보와 주요 위험 변화를 조직 단위로 요약해서 보고 싶다. 그래야 현재 작업 목록과 별개로 위험 변화의 규모와 반복 패턴을 파악하고 공유할 수 있다.

수용 기준:

- 선택한 기간의 신규 재검토 후보와 주요 변화 원인을 확인할 수 있다.
- 기간별 후보 수와 주요 변화 유형의 추이를 확인할 수 있다.
- 영향을 받는 저장소와 패키지의 분포를 확인할 수 있다.
- 시스템성 변동과 개별 재검토 대상을 구분할 수 있다.
- 요약 결과에서 개별 Alert 상세로 이동할 수 있다.

### US-06. 패키지 단위 조치 후보 확인

**우선순위: P1**

> 검토자로서, 동일 패키지 업데이트로 함께 해결할 수 있는 Alert를 묶어 보고 싶다. 그래야 해결 범위가 큰 작업부터 조치자에게 요청할 수 있다.

수용 기준:

- 패키지별 영향 저장소와 Alert 수를 확인할 수 있다.
- 연결된 취약점과 권장 수정 버전을 확인할 수 있다.
- 예상 해결 범위가 보장값이 아니라 후보임을 확인할 수 있다.
- 원본 GitHub Alert 또는 존재하는 Dependabot PR로 이동할 수 있다.

### US-07. 조건부 업데이트 수행

**우선순위: P1**

> 조치자로서, 조직이 허용한 고위험 패치의 업데이트 PR을 안전하게 생성하고 싶다. 그래야 반복 작업을 줄이면서 변경을 검토할 수 있다.

수용 기준:

- 자동조치 정책의 통과 또는 거부 이유를 확인할 수 있다.
- 허용된 저장소와 변경만 PR 생성 대상으로 선택된다.
- CI 실패 또는 허용 범위를 벗어난 변경은 자동으로 병합되지 않는다.
- 승인이 필요한 변경과 자동병합 가능한 변경이 구분된다.
- 병합 후 Dependabot에서 해결 상태가 확인될 때까지 처리 결과를 추적할 수 있다.

## 6. P2 — 프로젝트 기간 내 고려 항목

P2에는 프로젝트 기간 안에 검토할 수 있지만 아직 구현을 약속하지 않은 항목만 추가한다. 항목을 P0 또는 P1으로 승격할 때 사용자 가치, 우선순위와 수용 기준을 확정한다.

### US-08. AI Agent 검토 지원

**우선순위: P2 · 유형: User Story**

> 검토자로서, 위험 변화와 관련 자료를 요약하고 다음 검토 행동을 준비하는 도움을 받고 싶다. 그래야 여러 정보를 직접 정리하는 시간을 줄일 수 있다.

AI Agent는 근거와 출처를 제시하는 보조 역할로 제한하며 실제 악용 여부, 위험 수용 또는 자동병합을 단독 결정하지 않는다.

### US-09. 자산 위험도 매핑

**우선순위: P2 · 유형: User Story**

> 검토자로서, 저장소가 어떤 배포 자산과 서비스에 연결되고 조직에서 얼마나 중요한지 확인하고 싶다. 그래야 같은 취약점도 실제 고객 맥락에 맞게 검토할 수 있다.

P0에서 사용하는 저장소 중요도는 수동으로 관리하는 기본 맥락이다. 이 항목은 배포 환경, 서비스와 비즈니스 중요도를 연결하는 확장 범위다.

### US-10. 탐지·대응 효과 분석

**우선순위: P2 · 유형: User Story**

> 검토 책임자로서, 위험 변화 신호와 이후 검토·조치 결과를 기간·규칙·조직별로 비교하고 싶다. 그래야 탐지 규칙과 조직의 대응 방식을 개선할 근거를 찾을 수 있다.

분석 범위는 신호·규칙 버전별 처리 결과, 최초 검토와 수정 완료까지 걸린 시간, 조직·저장소·패키지의 반복 패턴과 시스템성 변동으로 제한한다.

수정 전환율이 낮다고 탐지 신호가 무효인 것은 아니며, 조치 결과만으로 실제 위험이나 규칙의 정확도를 확정하지 않는다. 분석 결과는 자동 규칙 변경이 아니라 사람의 검토 근거로 사용한다.

### T-01. Azure Key Vault 및 관리형 ID 연동

**우선순위: P2 · 유형: Task**

애플리케이션과 데이터 연동에 사용하는 비밀정보를 코드·설정 파일에서 분리하고 Azure Key Vault 및 관리형 ID로 접근한다. 구현 대상으로 선택되면 환경별 비밀정보 이전과 접근 검증 작업을 GitHub Issue에서 구체화한다.

### T-02. 운영 배포 보안 통제 적용

**우선순위: P2 · 유형: Task**

운영 배포에 필요한 최소 권한, 네트워크 접근 경계와 감사 로그 통제를 적용한다. 구체적인 통제 범위와 검증 작업은 배포 환경이 확정된 뒤 GitHub Issue에서 구체화한다.
