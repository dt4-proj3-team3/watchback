## 1. 제품과 문제

Watchback은 해결되지 않고 누적된 Dependabot Alert를 지속적으로 관찰하고, 위험이나 조치 가능성이 달라져 다시 볼 가치가 생긴 항목과 이유를 알려주는 서비스다.

개발팀은 많은 Alert가 쌓이면 모든 항목을 검토하거나 처리하기 어렵다. 별도의 판단 없이 남겨진 Alert도 시간이 지나면서 EPSS, KEV, CVSS와 패치 정보가 달라질 수 있다. 모든 변화를 다시 알리면 알림 피로가 반복되므로, 기존 backlog에서 우선순위가 새롭게 높아진 항목만 선별해야 한다.

> 코드는 그대로여도 위험은 달라질 수 있다. Watchback은 다시 볼 가치가 생긴 Alert를 놓치지 않게 한다.

### 확인된 근거와 검증할 가정

| 구분 | 내용 |
| --- | --- |
| 외부 근거 | SCA 실무자 연구에서는 많은 Alert를 먼저 severity, 수정 비용과 애플리케이션 중요도로 선별하며, 실제 영향 판단에는 추가 맥락과 수작업이 필요했다. ([USENIX Security 2025](https://www.usenix.org/system/files/usenixsecurity25-lin-elizabeth.pdf)) |
| 외부 근거 | 활발히 유지되는 JavaScript 프로젝트의 Dependabot 보안 업데이트 4,978건을 분석한 연구에서 16.25%가 미해결로 남았고, 업데이트가 많아질수록 미해결 비율이 증가하는 경향이 관찰됐다. ([Empirical Software Engineering 2025](https://link.springer.com/article/10.1007/s10664-025-10638-w)) |
| 외부 근거 | GitHub도 Alert를 동일하게 처리하지 않고 EPSS와 저장소 속성을 함께 사용해 우선순위를 정하도록 안내한다. ([GitHub](https://github.blog/security/application-security/cutting-through-the-noise-how-to-prioritize-dependabot-alerts/)) |
| 검증할 가정 | 누적 Alert 중 위험이나 조치 가능성이 달라진 항목만 제시하면 전체 backlog를 다시 확인하는 것보다 검토량을 줄일 수 있다. |
| 검증할 가정 | EPSS의 일시적·집단적 변동을 분리하면 단순 임계값보다 적고 안정적인 재검토 목록을 만들 수 있다. |

### 제품 가설

기존 Alert의 위험 및 조치 가능성 변화를 저장소 중요도와 함께 적용하고 일시적·집단적 변동을 분리하면, 전체 backlog를 반복 확인하지 않아도 되는 검토 가능한 규모의 목록을 만들 수 있다. 과거 검토 기록이 있다면 당시 판단과 현재 상태를 추가로 비교하고, 패키지 단위 묶음과 제한적인 업데이트 자동화를 통해 분석을 실제 해결까지 연결할 수 있다.

## 2. 사용자

아래 현재 처리 방식과 Pain Point는 공개된 SCA 사용자 연구와 GitHub 운영 자료를 바탕으로 구성한 사용자 가설이며, 실제 사용 과정에서 검증한다.

| 사용자 | 현재 처리 방식과 Pain Point | 필요한 것 |
| --- | --- | --- |
| 검토자 | 저장소별 Alert와 외부 위험 정보를 직접 확인하므로, 누적 backlog에서 무엇이 새롭게 달라졌는지 파악하기 어렵다. | 상황이 달라진 Alert와 선정 근거를 확인하고 재검토·조치 필요성을 판단 |
| 조치자 | 전달받은 Alert마다 버전 변경, PR, CI와 해결 상태를 각각 처리하므로 반복 작업과 사후 확인에 시간이 든다. | 요청받은 업데이트를 수행하고 PR부터 해결 확인까지 상태를 연결 |

조직에 따라 같은 사람이 두 역할을 모두 맡을 수 있다.

> 누적된 Alert의 상황이 달라졌을 때, 전체 backlog를 다시 확인하지 않고도 무엇을 왜 먼저 검토해야 하는지 알고 싶다.

## 3. 목표와 경계

### 목표

- 기존 backlog에서 위험이나 조치 가능성이 달라진 Alert를 선별하고 변화 근거를 설명한다.
- 고객의 저장소 중요도와 조치 가능성을 반영해 재검토 순서를 제시하고 결정 이력을 보존한다.
- 조직 단위 업데이트 후보와 허용된 고위험 항목의 조치를 실제 해결 확인까지 연결한다.

### 비목표

- Dependabot을 대체하는 취약점 탐지 제품을 만들지 않는다.
- 코드 도달 가능성이나 실제 악용 가능성을 직접 판정하지 않는다.
- 모든 취약점을 무조건 자동 수정하거나 패치 안전성을 보장하지 않는다.
- 전사 소프트웨어 자산과 공급망 전체를 관리하지 않는다.

## 4. MVP

### 핵심 흐름

```text
누적된 Alert와 초기 상태 관찰
→ 외부 위험 및 패치 정보 변화 감지
→ 시스템성 변동과 개별 변화 구분
→ 고객 Alert·저장소 중요도와 연결
→ 다시 볼 항목 선별 및 검토
→ 패키지 단위 조치
→ Dependabot 해결 상태 확인
```

### 출시 범위

| 출시 범위 | Capability | 사용자 결과 |
| --- | --- | --- |
| Committed | 위험 변화 비교 | 기존 Alert에서 무엇이 새롭게 달라졌는지 확인 |
| Committed | 시스템성 변동 분리 | 모델·피드 변경으로 인한 불필요한 재알림 억제 |
| Committed | 재검토 우선순위와 결정 이력 | 다시 볼 순서와 이유를 확인하고 판단을 보존 |
| Committed | Risk Drift Digest | 일정 기간 새롭게 위험해진 기존 Alert를 조직 단위로 파악 |
| Committed | Remediation Campaign | 한 번의 패키지 업데이트로 해결 가능한 범위 파악 |
| Committed | 조건부 자동 업데이트 | 허용된 KEV 항목을 PR·CI부터 해결 확인까지 연결 |
| Conditional | AI Agent 지원 | 변화 요약과 검토·조치 준비를 보조하되 보안 판단은 확정하지 않음 |
| Conditional | 자산 위험도 매핑 | 저장소를 배포 자산·서비스·비즈니스 중요도와 연결해 고객 맥락을 확장 |
| Conditional | 탐지·대응 효과 분석 | 위험 변화 신호와 이후 검토·조치 결과를 비교해 규칙 개선과 조직 대응의 근거 확인 |
| Conditional | 운영 보안 강화 | Key Vault와 접근·네트워크·감사 통제를 적용해 운영 환경의 보안 수준 강화 |

Committed Scope는 이번 프로젝트에서 제공하며 구현 순서는 제품 백로그의 P0·P1을 따른다. Conditional Scope는 P2로 관리하고 일정과 선행 조건을 확인한 뒤 포함 여부를 결정한다. 사용자 수용 기준은 제품 백로그에서 관리하고, 현재 스프린트의 설계·구현·검증 작업은 [SP1 Backlog](sp1-backlog.md)에서 구체화한다.

## 5. 데이터 범위

| 구분 | 데이터 |
| --- | --- |
| 외부·연동 데이터 | Dependabot Alert, GHSA, EPSS 일별 신호, CISA KEV |
| 고객 데이터 | 조직·저장소·담당자·저장소 중요도·검토 기록·업무 결정 |

외부 데이터의 출처와 기준 시점을 표시하고, 고객 데이터는 조직별 접근 범위 안에서 관리한다.

## 6. 성공 지표

Watchback은 실제 악용을 확정하거나 예측하는 모델이 아니다. 제품 성공 지표와 급등 규칙을 해석하기 위한 진단 지표를 구분한다.

### 핵심 KPI

| KPI | 계산 | 의미 |
| --- | --- | --- |
| 재검토 압축률 | `1 - 재검토 후보 수 / 전체 관찰 Alert 수` | 기존 backlog 대비 검토량을 얼마나 줄였는가 |
| 시스템성 변동 억제율 | `집단 변동으로 묶은 후보 수 / 단순 급등 기준 후보 수` | 모델·피드의 집단 변화로 발생할 개별 알림을 얼마나 억제했는가 |

### 규칙 진단 지표

| 지표 | 의미 |
| --- | --- |
| 급등 후 유지 기간 | 하루짜리 변동과 지속되는 변화를 구분하고 알림 대기시간을 조정하기 위한 값 |
| 추가 신호 동반 여부 | EPSS 외 KEV, 패치 또는 advisory 변화가 함께 있었는지 확인하기 위한 값 |
| 임계값별 후보 수 | 완화·기준·엄격 조건에 따라 검토량이 얼마나 달라지는지 확인하기 위한 값 |
| KEV 선행 사례와 선행 일수 | 일부 실제 악용 사례에서 EPSS 변화가 먼저 나타났는지 설명하기 위한 보조 사례 |

급등 기준은 실제 위험의 정답선이 아니라 재검토 후보를 만드는 운영 기준이다. 여러 임계값에서 핵심 KPI와 진단 지표가 어떻게 달라지는지 비교하고, 팀이 감당할 검토량과 결과의 안정성을 기준으로 선택한다. 진단 지표 자체를 높이는 것을 제품 목표로 삼지 않는다.

KEV는 핵심 KPI의 정답으로 사용하지 않고 보조 검증에만 사용한다. 과거 신규 KEV 사례 중 EPSS 변화가 등재 전에 관찰된 사례 수와 선행 일수를 제시하되, 이를 전체 실제 악용에 대한 정확도나 포착률로 일반화하지 않는다. KEV 등재 이후의 재검토는 별도로 `KEV 처리율`과 `케이스 생성 지연시간`을 측정한다.

재검토 압축률은 사용자의 업무량을 나타내므로 Alert 단위로 계산한다. 급등 변화 분석은 중복 저장소의 영향을 받지 않도록 고유 CVE 단위도 함께 제시하고, 영향 저장소·Alert 수는 조직 영향으로 별도 집계한다. 초기 분석으로 기준선과 적정 검토량을 확인한 뒤 목표값을 확정한다.

## 7. 제약 및 의존성

- 탐지 범위와 저장소 정보는 Dependabot 및 GitHub API에 의존한다.
- 위험 변화 판단은 EPSS·KEV·GHSA의 갱신 시점과 데이터 품질에 영향을 받는다.
- 고객별 결과는 저장소 중요도와 고객 맥락 정보의 품질에 영향을 받는다.
- 시스템 구성, 데이터 흐름과 책임 경계는 [Technical Architecture](../architecture/technical-architecture.md)를 따른다.
